## P1: auction keyword help still aborts the server

All four aborts share this stack:

```text
__pthread_kill / raise / abort
__fortify_fail / __chk_fail
___snprintf_chk
snprintf
auction_list          economy/auction_houses.c:1923
new_ah_call            economy/auction_houses.c:1291
command_interpreter
dispatch_playing_command / session input / game_loop
```

Every core has the same formatting state: `count == 27`, `i == 1`, destination
buffer size 65,536, requested `maxlen == 65536`, but only `slen == 65509` bytes
remain at `buff + count`. The invalid list argument is `plate` in three cores and
`1` in the fourth. The first keyword, `horns`, has already been printed.

The SQL implementation of
[auction_list()](../../src/economy/auction_houses.c), lines 1919–1926 in the
reviewed checkout, appends with:

```cpp
count += snprintf(buff + count, MAX_STRING_LENGTH, ", %s",
                  sorter->getKeyword(i).c_str());
```

That claims the full buffer capacity after advancing the destination pointer.
The build enables `_FORTIFY_SOURCE=3`; libc rejects the false bound and aborts
before writing the second keyword. This does **not** require a long input,
large auction catalogue, actual overflow, or SQL failure. An ordinary player
entering an unsupported list form reaches the syntax/keyword help and terminates
the whole process.

The same mistake appears in the empty `auction list sort` help path at lines
1870–1877. Both paths also pass the full capacity for their final `".\n\r"`
append. The four historical dumps hit the unsupported-mode branch; the second
branch is an independently reproduced variant of the same defect. The flat-file
implementation has separate list/help code and does not contain these appends.

### Current-source reproduction

An isolated probe compiles the **unchanged SQL `auction_list()` and production
`half_chop()`** from the checkout with `g++ -std=c++20 -O2 -g -D_FORTIFY_SOURCE=3`.
It supplies the first two production keywords (`horns`, `nose`), a synthetic
character handle, and stubbed output/SQL adapters. It does not boot a server,
connect to a database or use player data. Core creation is disabled for the probe.

| Input to the auction command | Result |
| --- | --- |
| `list plate 1000`, `list plate`, `list 1`, `list sort` | SIGABRT, subprocess return `-6`, `*** buffer overflow detected ***: terminated` |
| `list`, `list all`, `list sort horns`, `list player Synthetic` | Return 0 |

This proves the current command formatter still fails at the observed boundary.
The successful cases establish routing controls with synthetic empty query results,
not full auction functionality. Probe source, runner, binary and results are in
the ignored `bin/analysis/core-dump-audit-2026-10-18/` directory:
`reproduce_auction_list.py`, `auction_list_probe.cpp`, `auction_list_probe`, and
`auction_list_probe.txt`.

No covering PR was found: all six open PRs at review time (#190, #191, #193,
#194, #195, #196) concern Nexus or its migration prerequisites. Their complete
changed-file lists do not touch this formatter. Recent closed/merged PRs and
the file history were also reviewed; latest master still contains the exact
failing implementation. Existing auction transaction tests check routing and
persistence contracts rather than executing this SQL keyword-help path.

### Remaining work

- Repair **both** keyword-help append loops and their final suffixes. Use the
  existing bounded append facility or accurate remaining capacity, and handle
  truncation without advancing a cursor beyond the buffer. Keep hardening enabled.
- Add an executable regression around the production SQL command path using
  `-O2 -D_FORTIFY_SOURCE=3`. Cover the four failing forms above, arbitrary invalid
  modes, empty sort help, and valid unfiltered/player/keyword forms. ASan alone
  need not catch a false capacity declaration when the short output fits.
- Run the focused regression and relevant auction tests, build the server, and
  verify the commands on an isolated SQL-backed runtime before claiming repair.
  Register the regression in the normal test discovery. Deployment is separate.

## Addressed: staff player purge

Both SIGSEGV dumps stop at `writeCharacter()` (`core/files.c:1311`) called from
`do_purge()` (`cmd/actwiz.c:5371`). In each, the victim has `only.pc == NULL`,
`desc == NULL`, and `in_room == NOWHERE`; the faulting instruction reads
`0x80(%rax)` with `rax == 0`, producing fault address `0x80`.

The old purge path extracted the victim, then passed it to `writeCharacter()`
and attempted further descriptor/free cleanup. Merged
[PR #186](https://github.com/LuminariMUD/Duris/pull/186), commit `89253179a`,
replaces that continuation with an accepted empty-inventory save before drops,
then one `extract_char_after_terminal_save(vict)` and no subsequent victim
dereference. The repair is present in
[do_purge()](../../src/cmd/actwiz.c), including line 5459.

Fresh verification: `python3 tests/async/test_actwiz_player_purge.py` passed all
30 ASan/UBSan cases across SQL and flat-file configurations. Its terminal-extraction
fixture frees the victim, so a subsequent stale access is observable. It also
checks save refusal, inventory preservation, transient/nested items, merged coins,
lockers and pending transactions. Save/account/floor services are stubbed; this
audit does not claim a new purge/reconnect/restart gameplay journey.
